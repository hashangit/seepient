The journey of a message

What happens when you type something and hit enter, top to bottom.

1
You talk through an adapter — the terminal app, the code library, or the network server.
2
The adapter hands your message to the Agent Loop, the single engine that runs everything.
3
The loop asks an AI provider (OpenAI, Anthropic…) what to do next.
4
If the AI wants to do something, the loop runs a tool — shell, files, search, email…
5
Results flow back up the same path and you see the answer.

Layer 1 — Adapters

"the ways in"

Three different front doors, all leading to the same engine. They handle everything user-facing — keypresses, screens, HTTP requests — then pass a clean request downward.

CLI — the terminal app src/adapters/cli/

What runs when you type seepient. Shows a full-screen chat UI in a modern terminal, or a plain text prompt as fallback. Also handles /commands and setup.

SDK — the code library src/adapters/sdk/

What you import in your own JavaScript/TypeScript project: generateText(), streamText(), createAgent().

Server — the network service src/adapters/server/

Exposes Seepient over HTTP + WebSocket so other programs can use it remotely. Handles API keys and sessions.

all three doors hand your request down to…

Layer 2 — Core

"the engine room"

Everything that decides what to do with your request, with no idea which door you came through. This independence is what makes the design good — and it's worth protecting.

Agent Loop — the one engine src/core/agent-loop.ts

The heart of the system. Every request from every adapter goes through this single loop: ask the AI, run the tools it requests, repeat until done. There is exactly one of these — no copies.

Tool Runner src/core/tool-executor.ts

When the AI says "run this tool", this finds it, checks it's allowed, runs it, and hands back the result.

Provider Picker src/core/provider-resolver.ts

Decides which AI company to talk to based on your config, env vars, or defaults.

Permission System src/core/permission.ts · grants.ts

Decides which tools the AI may use and when to ask you first. Remembers your "always allow" grants at session, project, or global scope.

Hooks src/core/hooks.ts

Safety checkpoints before and after each step. Built so a failing hook can never crash the loop.

Session Store src/core/session-store.ts

Saves conversations to disk (or memory) so you can pick up where you left off.

Settings src/core/settings-manager.ts

The /settings system — 31 validated config keys, saved across runs.

Hashline src/core/hashline/

The hash-anchored edit engine — lets the AI make surgical line-level edits to files by referencing content hashes instead of line numbers.

Middleware — loop add-ons src/core/middleware/

Optional wrappers around the loop: logging, rate-limiting, auth. Fine here — except one file, below.

wrong place

Semantic Tool Injection src/core/middleware/semantic-tools.ts

Picks which external (Gateway) tools match your message and injects them into the AI's options.

Reaches upward into the Gateway layer →
awkward spot

Skill Invoker src/core/skill-invoker.ts

Handles /skill-name requests: finds the skill, fills in its arguments, builds the final prompt. Useful to all adapters — but it does its job by digging through Skills' internals.

Reaches across into Skills internals →
the engine delegates the actual work down to…

Layer 3 — Infrastructure

"the workers"

The parts that touch the outside world: AI company APIs, your filesystem, the network, external tool servers. The rule of the house: only Providers may talk to AI vendor SDKs, and Core should never know these layers' details.

Providers — the AI translators src/providers/

The only code allowed to speak to OpenAI and Anthropic SDKs. Translates Seepient's generic requests into each vendor's format, so the rest of the system never cares which AI it's using.

Tools — the hands src/tools/

Fifteen built-in abilities: run shell commands, read/write/edit files, search the web, send email, take screenshots, render widgets, manage the todo list… Two of them break the rules — see below.

rule breakers

Image & Prompt-Optimizer tools src/tools/image.ts · prompt-optimizer.ts

Generate images (DALL-E) and rewrite prompts. Useful — but they import the OpenAI SDK themselves instead of going through Providers.

Imports the OpenAI SDK directly, bypassing Providers →
awkward spot

use_skill tool src/tools/index.ts

The tool that activates a skill when the AI asks for one. It works — but it imports the Skills registry directly, tying two layers that were meant to stay independent.

Reaches across into the Skills layer →

Skills — the knowledge packs src/skills/

Markdown files that teach the agent specialist knowledge (e.g. "how to review code"). Found on disk, loaded only when needed, size-limited so they can't flood the AI's memory.

Gateway — the external connector src/gateway/

Connects to outside MCP tool servers, imports their tool lists, and scores which ones are relevant to your message. Correctly depends on Core (not the other way around) — except Core's middleware reaches back up into it.

Bug — still broken

The two branching bugs (permission prompt, 50 type errors) are fixed. This one is a design issue that predates the branch.

1

Image & prompt-optimizer tools silently bill OpenAI regardless of your provider

Pick Anthropic as your provider, ask for an image, and the request still goes to OpenAI — failing if you have no OpenAI key configured, or billing an account you didn't intend. Both src/tools/image.ts and src/tools/prompt-optimizer.ts import the OpenAI SDK directly.

Fix: route both through the Providers layer, same as every other AI call. (Deferred — to be handled separately.)

What's out of place — and why it matters

Design-level placements that violate the house rules. All four are still present after the rebase.

1

Two tools call OpenAI directly, skipping the translator layer

src/tools/image.ts and src/tools/prompt-optimizer.ts import the OpenAI SDK themselves. Every other part of the system goes through Providers — these two don't. This is both an architecture violation and the user-facing billing bug above.

Fix: route both through the Providers layer — add an image-generation / prompt-optimization capability behind the provider interface, so the vendor swap happens in one place like everything else.

2

Core's middleware reaches up into Gateway

src/core/middleware/semantic-tools.ts imports Gateway code directly. The engine room isn't supposed to know the external connector exists — you can't remove or swap Gateway now without editing Core. Dependencies should only ever point down.

Fix: move this middleware out of Core (e.g. into a shared adapters folder) and let each adapter wire it in. Core should expose a generic "inject tools" hook, not import Gateway itself.

3

The use_skill tool is glued to the Skills layer

The tool that activates skills imports the Skills registry and internals directly (src/tools/index.ts). Tools and Skills were designed as independent siblings — this makes them co-dependent, so neither can change shape without touching the other.

Fix: have the Skill Invoker (or the loop) own skill activation; the tool should just declare intent ("activate skill X") and let the layer above do the work.

4

Skill Invoker lives in Core but does adapter-grade orchestration

src/core/skill-invoker.ts parses user input, resolves files, builds prompts, and manages provider switching — coordination work that belongs to the layer above. It's shared by all adapters (which is why it landed here), but it makes Core depend on Skills' internals.

Fix: acceptable as-is if documented as a shared adapter helper — or move it to src/adapters/ so Core stays clean. Lowest priority of the four.

Current state: clean compile, all tests pass, all modules present. The architecture itself is sound — one engine, three doors, clear layers. The four design issues above are deliberate improvements, not emergencies. Nothing currently enforces the layering, though — no lint rules, no import checks, just one CI grep keeping React out of headless builds.

Seepient through the six-layer lens

The architecture-setup skill's generic model — UI → Transport → Domain → Capabilities → Vendors, with Foundations as the shared base — laid over this codebase. Does it fit? Yes: it turns out the model is already here, wearing different names.

Seepient's three layers are the six layers with two fused pairs. Adapters = UI + Transport. Core = Domain + Foundations. Infrastructure = Capabilities + Vendors. Adopting the lens needs no restructuring — it gives precise names to the two real violations on page 1, and something concrete to point lint rules at.

Layer 1 — UI / Presentation

"what the user sees and touches"

Understands what the user did and expresses intent. Renders, captures keypresses, parses arguments — and knows nothing about how work actually gets done.

TUI — the terminal chat src/adapters/cli/tui/

The full-screen Ink/React interface: components, widgets, overlays, diff viewer, logo. Pure rendering and input.

REPL fallback src/adapters/cli/repl.ts

Plain-text prompt for pipes, Docker, and non-TTY environments.

Command definitions src/adapters/cli/index.ts

Commander wiring: flags, arguments, and choosing TUI vs REPL launch mode.

SDK public surface src/adapters/sdk/index.ts

A library's UI is its entry point: generateText(), streamText(), createAgent().

Server — deliberately absent

Per the skill's own rule: a service/daemon has no UI layer. Its top layer is Transport.

intent becomes a validated, authenticated request

Layer 2 — Transport

"the gatekeepers"

The single checkpoint between outside and inside: receive the request, validate input, check authentication and permissions, delegate downward. Strictly no business logic or product decisions.

Server auth src/adapters/server/auth.ts

API keys and scopes — the gatekeeper in its purest form.

REST & WebSocket handlers server/rest.ts · ws-handlers.ts · settings-handlers.ts

Validate incoming requests, hand them to Core, make no product decisions of their own.

CLI bootstrap & slash commands cli/index.ts · cli/commands/

Merge config layers, resolve the provider, dispatch /commands, hand a clean session to Core.

SDK option resolution sdk/agent.ts · sdk/settings.ts

Turn caller options into a valid loop configuration before anything runs.

clean requests only — no product decisions made yet

Layer 3 — Domain

"the brain"

The product and business decisions — the use-cases and rules that would survive a full rewrite of the UI, the transport, or any vendor.

Agent Loop src/core/agent-loop.ts

The heart of the system, exactly as on page 1. Under this lens it's precisely what "Domain" means: ask the AI, run the tools, repeat until done.

Tool Executor src/core/tool-executor.ts

Decides which tools exist, which are allowed, and how results come back.

Permissions & Grants core/permission.ts · grants.ts

The policy decisions: what may run, when to ask, what to remember.

Hooks & Middleware core/hooks.ts · core/middleware/

The pipeline rules around each step — logging, rate-limit, auth as loop-level concerns.

Skill orchestration core/skill-invoker.ts · skill-catalog.ts

Decides what a skill request means: fill arguments, build the prompt, switch provider if the skill asks.

Streaming core/stream-manager.ts · stream-accumulator.ts

How partial answers queue, accumulate, and reach every adapter the same way.

Sessions & Settings logic core/session-store.ts · settings-manager.ts

The rules for persistence, TTL, and the 31 validated config keys.

Hashline patch engine src/core/hashline/

The grammar and patcher behind surgical, hash-anchored file edits.

Provider choice & context accounting core/provider-resolver.ts · tokenizer.ts · context-breakdown.ts · message-convert.ts

Which provider, how much context, what message shape — decisions, not vendor calls.

generic operations — "chat", "run tool", "load skill" — never vendor specifics

Layer 4 — Capabilities

"stable internal APIs"

The integration boundary for external-ish concerns. Each exposes a generic operation and hides the vendor behind it — swapping a provider changes this layer only, and the Domain never notices.

Providers src/providers/

The LLMProvider interface + factory: one generic chat(), four provider types behind it.

Tools src/tools/

Fifteen abilities behind one ToolModule contract — shell, files, web, email, widgets, todos…

Skills src/skills/

Registry, loader, parser, resolver — knowledge packs behind a single stable API.

Gateway src/gateway/

External MCP / OpenAPI tool servers, imported and scored so they look like ordinary tools.

Persistence backends session-store.ts — file & memory

Swappable storage behind the PersistenceBackend interface; custom backends register by name.

the only layer allowed to import a vendor SDK

Layer 5 — Vendors

"the edge — quarantined"

Actual third-party SDKs and external systems. Nothing outside this layer imports a vendor SDK directly — and that's a rule Seepient mostly keeps, with two known breaches.

OpenAI SDK wrapped by providers/openai.ts

Chat for openai and openai-compatible types. Should also serve the image and prompt tools — but doesn't.

Anthropic SDK wrapped by providers/anthropic.ts

Also serves GLM via the api.z.ai base URL — one vendor wrapper, two provider types.

MCP / OpenAPI servers wrapped by src/gateway/

External tool servers stay behind the Gateway; nothing else speaks their protocol.

The UI kit Ink · React · Commander · ws · figlet

Frameworks are vendors too — quarantined inside the TUI/CLI, exactly as the model prescribes.

quarantine breach

Image & prompt-optimizer tools src/tools/image.ts · prompt-optimizer.ts

Capability-layer code importing the OpenAI SDK directly. Page 1's billing bug — here it becomes a named, lint-detectable offense.

Vendor import outside the Vendors layer →
and underneath everything, the shared base

Layer 6 — Supporting Foundations

"the shared soil"

Shared schemas, contracts, and persistence. The upward exception: any layer above may import Foundations — Foundations imports from no one. Today these files live inside src/core/, which is fine physically, as long as the rule holds.

Core contracts src/core/types.ts

Messages, tools, hooks, agents, sessions — the vocabulary every layer speaks.

Error hierarchy src/core/errors.ts

SeepientError with code + retryable — one failure language for all layers.

Settings schema src/core/settings-schema.ts

The 31 dot-key settings: validation, env vars, categories. Transport validates against it; Domain manages it.

Config & model catalog core/config.ts · src/models-catalog.ts

The merge layers (env → local → global → defaults) and the known-model list.

Session files on disk ~/.seepient/sessions/

The closest thing to a database — the persistence the Foundations layer owns.

Flow test — "generate an image and save it to /tmp"

The skill's check: trace a real request. If any step skips a layer, the design is wrong.

1
UI: the TUI captures your message and expresses intent. It has no idea how images happen.
2
Transport: CLI bootstrap resolves config and permission mode, hands a clean request down. (Server would also check your API key here.)
3
Domain: the agent loop plans; the permission system checks your generate_image grant; the tool executor dispatches.
4
Capabilities: the image tool runs behind the generic tool interface — "generate an image", nothing vendor-shaped.
5
Vendors: the call should reach OpenAI Images via Providers. Today the tool imports the SDK itself — the page-1 bug lives exactly at this seam.
6
Foundations: message types, error codes, and the session file carry the whole exchange, top to bottom.

What adopting the lens would buy

No restructuring — but sharper names, and rules a linter can actually enforce.

1

The two real violations get a name — and a tripwire

src/tools/image.ts and src/tools/prompt-optimizer.ts are vendor-quarantine breaches. One import lint rule — no openai or @anthropic-ai/sdk outside src/providers/ — makes this class of bug impossible, not merely known.

2

Foundations stop being anonymous

types.ts, errors.ts, settings-schema.ts, config.ts are currently "just more files in core/". Naming the base layer adds its one rule — Foundations import from no one — which is exactly what keeps shared types from becoming a coupling magnet.

3

One page-1 badge softens

Core's middleware importing Gateway is Domain → Capability — the legal direction in this model. It's still tidier when adapters wire it in, but it isn't a rule-break. Being honest about which "violations" are actually violations is part of what a layer map is for.

4

Nothing moves physically

The skill says: pick the simplest layout that can still enforce the dependency rules. That's six conceptual responsibilities expressed in the three existing directories — documented here, enforced by lint. The map changes; the code doesn't have to.

Deliberate deviations, per the skill's own rules

The skill allows dropping or merging layers — as long as it's deliberate and said out loud.

1

Server has no UI layer

A daemon's top layer is Transport. Not missing — deliberately absent.

2

UI and Transport stay physically fused in src/adapters/

The split is conceptual: each adapter file does one job or the other, and the boundary is worth naming even where it isn't worth a new directory.

3

Vendors is a rule, not a folder

The vendor layer is a quarantine over package.json dependencies, enforced by lint — exactly as the skill prescribes for a project this size.

Verdict: the six-layer model fits — because Seepient was already built this way, just with coarser labels. Same house, better room labels. What it adds is precision: the two real violations get names a linter can enforce, and "where does new code go?" gets a sharper answer.

The target folder system — and what must change to get there

Page 2 showed the six layers already exist conceptually. This page makes them physical: six directories under src/, a dependency audit of everything built so far, and the exact refactor list that closes the gap.

What we built mostly fits — the brain is right, the edges are wrong. The Domain (agent loop, permissions, hooks, middleware, orchestration) needs no redesign at all. The work is at the seams: contracts living in the wrong folders, two vendor-quarantine breaches, two arrows pointing the wrong way, and adapters fusing two jobs. Roughly 80% of it is moving files and rewriting import paths; only three items are true redesigns.

The refactor list — real violations first

Found by scanning every cross-directory import against the rules above. Red = wrong-direction or quarantine breach. Amber = structural coupling.

1

Create capabilities/media/ — fixes the billing bug and the quarantine breach

tools/image.ts and tools/prompt-optimizer.ts import the OpenAI SDK directly — so image generation bills OpenAI no matter which provider you chose. The capability exposes generateImage() / optimizePrompt() behind a vendor-neutral interface; the OpenAI-backed implementation lives in vendors/openai.ts. The tools become thin handlers.

Type: true redesign #1 — small new abstraction, deletes a user-facing bug.

2

Flip the Gateway arrow — Domain pulls, Capability never pushes

gateway/index.ts currently imports registerTool from core/tool-executor.ts — a Capability reaching up into Domain (page 1 blessed this; the six-layer model condemns it). Instead the Gateway just exports its tool modules, and the composition root wires them into the Domain's registry at startup.

Type: true redesign #2 — registration moves to the composition root; both sides get simpler.

3

Move core/tokenizer.ts → capabilities/tokenizer/

The second vendor breach: gpt-tokenizer is imported inside Domain. The tokenizer is a stable counting API over a vendor library — a textbook Capability, wrapping vendors/gpt-tokenizer.ts.

Type: move + one import redirect. Mechanical.

4

Bring use_skill activation home to Domain

tools/index.ts imports the Skills registry, arg substitution, and body limiter — sideways Capability→Capability coupling. The tool shrinks to declaring intent ("activate skill X"); domain/skills/ (the skill invoker, which already legally imports the Skills capability) does the work.

Type: true redesign #3 — the page-1 "awkward spot" dissolves.

The refactor list — structural moves, no behavior change

Pure relocations and extractions. The 532-test suite is the safety net; tsc NodeNext means moves are import-path rewrites, nothing more.

5

Extract contracts into foundations/contracts/ — kills four edge classes at once

ToolModule/ToolDefinition (from tools/interface.ts), LLMProvider + message types (from providers/types.ts), the Middleware type (from core/middleware.ts), and the presentation contracts (WidgetSpec, FileWriteMetadata) are the vocabulary of three-plus layers. Moving them turns the sideways edges (providers→tools, gateway→tools), the types↔middleware foundation cycle, and the UI→tools type imports into legal Foundation imports — without touching any logic.

6

Move core/hashline/ → foundations/hashline/

The patch engine imports nothing but errors.js — a self-contained language, not a Domain decision. This move fixes the tools/edit-file.ts upward edge with zero code changes.

7

Create vendors/ — make the quarantine physical

Thin wrappers for openai, @anthropic-ai/sdk, @modelcontextprotocol/sdk, gpt-tokenizer, playwright, nodemailer, jsdom. Providers, Gateway, tokenizer, and the browser/email/website tools import from the wrapper instead of the package. Now the rule "no service-SDK imports outside vendors/" is one lint line. UI frameworks (Ink, React, Commander, ws) stay as the sanctioned substrate of ui/ — a stated, deliberate exception.

8

Split adapters/ into ui/ + transport/

The mechanical half of the restructure — each adapter file already does one job or the other (rendering vs validating/delegating), it just lives in a fused directory. Two mid-UI spots currently call createProvider directly (tui/index.tsx, setup.ts); those reroute through the Domain's existing provider-resolver.

9

Finish the Foundations: persistence backends, prompts, schema files

Session file/memory backends → foundations/persistence/; system-prompts.ts → domain/prompts/ (prompt text is a product decision); config.ts and models-catalog.ts stop importing ProviderType from the providers folder and take it from foundations/contracts/ (free, once #5 lands).

10

Enforce it, or it didn't happen

Boundary lint rules (dependency-cruiser or no-restricted-imports per directory), one file-casing standard, and pnpm supply-chain guards (minimumReleaseAge, onlyBuiltDependencies) — the skill's step 4. Without this, pages 2–3 are aspirational.

What already fits — no redesign needed

The brain is right. agent-loop · tool-executor · permission/grants · hooks · middleware pipeline (compose, logging, rate-limit, auth, semantic-tools) · stream-manager/stream-accumulator · session TTL logic · settings-manager · skill-invoker/skill-catalog · provider-resolver chain · the provider factory pattern · all of Skills' internals (registry, loader, parser, resolver) · Gateway's scorer and OpenAPI importer internals · the error hierarchy. These change address, not shape. That is the signal the original three-layer design was sound — the refactor is about knowledge boundaries, not re-engineering.

Migration order

Sequenced so every step lands on green tests.

1
Contracts first. Extract foundations/contracts/ (#5) — everything else depends on where the types live.
2
Foundations. hashline, persistence, schema files (#6, #9). Pure moves.
3
Vendors + capabilities. Wrappers, media capability, tokenizer (#1, #3, #7) — the breaches close here.
4
Arrow flips. Gateway registration and use_skill (#2, #4), then the adapter split (#8).
5
Enforce. Lint boundaries + naming + supply-chain guards (#10), verified by the skill's violation test.
Bottom line: the six-layer folder system is worth adopting — the audit shows the current code already respects it at the center and breaks it only at the edges. Three real redesigns (media capability, gateway registration flip, use_skill activation), a contracts extraction, and a mechanical directory split — then lint rules so the map stays true after the refactor ends.
